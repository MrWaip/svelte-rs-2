# PRD: Серверный трансформ (корневой)

label: transform-server
topics: server transform, SSR, target, rune erasure, state, derived, effect, props, store, assignment, svelte_transform_server

Корневой PRD для слоя серверного трансформа (`svelte_transform_server`) — script-половины backend'а `generate: server`. Клиентский аналог — `transform.md`.
Принцип: **dumb transform** — мутирует JS AST по готовым ответам анализа, новых данных анализа не производит.

## Назначение

Мутирует JS instance/module-скрипта под рантайм `svelte/internal/server`: стирание рун в серверные формы (`$state(10)` → голое значение, `$effect` — удаление, `$derived` — одноразовое вычисление), пропсы, сторы, присваивания.

## Скелет обхода

Один проход по программе через `oxc_ast_visit::VisitMut` — без `oxc_traverse`/`Scoping`: скоупы и имена резолвятся нашим `ComponentSemantics`, oxc-scoping не используется. Центральная структура `ServerTransform` реализует `VisitMut` только как тонкий диспатч «узел → обработчик»; вся логика — в `impl ServerTransform`-блоках модулей, по модулю на конструкцию. Новая серверная мутация скрипта = новый модуль с обработчиком + одна строка диспатча; второй проход по программе не заводится.

Ошибки — паник нет нигде; собственного error-типа слой не заводит (зеркально клиентскому трансформу): расхождение формы узла с семантикой и нереализованные формы — guard-скип, узел остаётся нетронутым.

## Inputs / outputs

- Входы: `&AnalysisData` (через `CompileContext`), `JsAst<'a>` (instance + module `oxc::Program`), allocator.
- Выход: мутированные `oxc::Program`-ы, готовые для серверного кодгена.

## Архитектурные инварианты

1. **Зеркальная граница слоёв.** Серверный трансформ своим единым проходом мутирует весь JS, нужный SSR — instance/module-скрипт и JS-выражения шаблона (из арены), — но о структуре шаблона (элементы, фрагменты, HTML) не знает ничего: её эмитит серверный кодген (`codegen-server.md`). Переписывание ссылки в серверную форму (store-чтение → `$.store_get`, `$$props` → `$$sanitized_props`) идёт по вердикту `ReferenceSemantics` и едино для скрипта и template-выражений.
2. **Только доменные вердикты анализа.** Утёкшие emit-формы (`DerivedEmit`, `PropEmitMode`, `ComponentAttachEmit`, `ComponentPropMemo`, …) читать и копировать запрещено: когда нужен факт, лик сначала рефакторится в доменный вердикт (клиентский потребитель переходит на «вердикт → форма» на своей стороне), затем потребляется. Механическая проверка: `grep Emit` по крэйту пуст.
3. **Одно решение — в одном месте.** Форму переписывания конструкции скрипта выбирает один исчерпывающий match по семантике; если ветка хочет второй запрос к анализу через `&&` — недостающий вердикт добавляется в анализ, не склейка здесь.
4. **Dev — ось эмита с первого дня.** Каждая фича приземляется в prod- и dev-формах одновременно; второй проход по всем визиторам не планируется.

Плюс общие инварианты слоя трансформа: не производит данных анализа, не эмитит диагностик, не пере-walk'ает AST за переклассификацией.

## Анти-паттерны

- Чтение `*Emit*`-типов из анализа.
- Знание о шаблоне / эмиссия шаблонных строк.
- Пересчёт rune-kind / реактивных фактов инспекцией AST.
