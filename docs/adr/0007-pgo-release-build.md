# 7. Релизный napi-аддон собирается с PGO

Статус: принято (2026-07-26)

## Контекст

Профиль компилятора плоский: после `lto = "fat"` + `codegen-units = 1` ни одна функция не
даёт больше ~4% self-времени. Работа размазана по ~15 обходам JS/template-AST, печати JS
через `oxc_codegen` и парсингу через `oxc_parser`. Замеры на корпусе реального приложения
(46 компонентов, от 20-строчных иконок до 700-строчных):

- слияние шести валидаторов инстанс-программы в один обход — −1%;
- ленивая аллокация `NodeTable`/`NodeBitSet` — −0,5%;
- пул арен `oxc_allocator` вместо арены на компиляцию — 0%;
- `-C target-cpu=native` — 0%.

То есть точечные оптимизации упираются в единицы процентов: узкого места нет, есть много
ветвлений и промахов предсказателя на дереве вызовов, где горячая ветка не видна компилятору
статически. Это ровно тот класс нагрузки, который лечится профилем.

## Решение

Публикуемый napi-аддон собирается с profile-guided optimization: инструментированная сборка →
прогон по корпусу репозитория → `llvm-profdata merge` → сборка с `-Cprofile-use`.

Пайплайн — `scripts/pgo.sh`, рецепты `just build-napi-pgo` (аддон) и `just build-bench-pgo`
(`bench_once` для замеров). Тренировочный корпус — `tasks/benchmark/benches/compiler` +
`tasks/compiler_tests/cases2` (1219 файлов), каждый компилируется в четырёх режимах
(`client|server` × `dev|prod`). Дополнительные корпуса — через `PGO_CORPUS`, число проходов —
через `PGO_ROUNDS`.

Эффект на том же корпусе из 46 компонентов, через napi (то, что мерит `just bench-breakdown`):
**−12,5% по сумме, −13,8% по geomean**; на мелких файлах −14,6%, на крупных −12,3%. Профиль,
снятый на корпусе репозитория, переносится на посторонний код без потери выигрыша.

## Инструментированная и оптимизированная сборка — одна и та же команда cargo

Тренировать нужно тем же вызовом cargo, которым потом собираешь. Символы Rust несут
disambiguator юнита (`_RNvMCsi0KDXpVNEBn_11svelte_span…`), а PGO матчит профиль по mangled-имени.
Профиль, снятый с хостовой сборки `cargo build -p benchmark`, для napi-сборки (cargo с явным
`--target`) не матчится ни на одной функции: 5340 предупреждений «no profile data available for
function», выигрыш 0%. Поэтому у `scripts/pgo.sh` две ветки — `napi` (инструментируется сам
аддон, тренировка через Node, `scripts/pgo-train.mjs`) и `bench` (инструментируется
`pgo_train`, тренировка нативная), и смешивать их нельзя.

## Последствия

- Выход компилятора PGO не меняет: это только layout кода и решения по инлайну. Гейты
  (`just test-compiler`, `just test-diagnostics`) те же.
- Релизная сборка становится двухпроходной и требует `rustup component add llvm-tools-preview`.
  Обычный `npm run build:release` продолжает работать и остаётся дефолтом для разработки.
- Профиль стареет вместе с кодом: он снимается заново на каждой сборке, отдельного
  закоммиченного `.profdata` в репозитории нет.
